# ADR-0004: Идемпотентное создание Job по request_key

- **Дата:** 2026-11-14
- **Статус:** Accepted

## Контекст и ограничения

Пользователь может дважды нажать кнопку поиска, UI может повторно отправить команду после задержки, а CLI — повторить запрос после неопределённого результата. Без защиты создаются дублирующие сетевые запросы и несколько Job для одного действия. HTTP-заголовок `Idempotency-Key` неприменим, поскольку BookScout не предоставляет HTTP API.

## Решение

Каждая команда `jobs.create`/`jobs.retry` содержит UUID `request_key`. Ключ сохраняется в SQLite с уникальным ограничением. Повтор команды с тем же ключом возвращает исходный `job_id`, текущее состояние и `replayed=true`, не создавая новую Job и не повторяя вызовы магазинов. Новая осознанная попытка (кнопка «Повторить») получает новый ключ и создаёт новую Job с `parent_job_id`.

UI создаёт один `request_key` на одно намеренное действие поиска, блокирует кнопку отправки на время обработки события и сохраняет ключ до получения подтверждения. Дублирующие события клика (в том числе с интервалом 100 мс) используют тот же ключ. При потере ответа клиент повторяет ту же команду с тем же ключом и payload; Dispatcher возвращает прежнюю Job. Уникальный индекс SQLite разрешает гонку двух конкурентных отправок: проигравшая транзакция перечитывает запись и возвращает существующую Job. CLI-клиент обязан повторно использовать тот же ключ, если повторяет одну и ту же команду после неопределённого результата.

## Рассмотренные альтернативы

1. **Только debounce в UI.** Отклонено: не защищает CLI, повтор после рестарта и повтор на уровне Dispatcher.
2. **Сравнение только по одинаковому ISBN и времени.** Отклонено: две намеренные проверки одного ISBN могут быть легитимными; эвристика ошибочно склеит запросы.
3. **HTTP Idempotency-Key.** Отклонено: HTTP API в архитектуре desktop MVP отсутствует.

## Цена решения

- Клиент обязан сохранять ключ для повторной отправки одной команды.
- Нужны уникальный индекс, транзакция создания Job и политика хранения ключей вместе с историей Job. Клиент обязан сохранять pending `request_key` до отправки, чтобы повтор после потери ответа использовал прежний ключ.
- Ошибочное повторное использование ключа для другой команды вернёт исходную Job; Dispatcher сравнивает hash нормализованного payload и возвращает `409 IDEMPOTENCY_KEY_REUSED`, если payload отличается.

## Условия пересмотра

Пересмотреть ADR при переходе на сетевой API (тогда можно добавить HTTP-заголовок как транспортное представление того же ключа), при необходимости ограничить срок хранения ключей или при изменении модели повторов.
