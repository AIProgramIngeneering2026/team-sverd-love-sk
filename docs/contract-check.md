# Проверка контрактов колодой K1–K10 и Джокером

**Область проверки:** локальный протокол JSON-команд BookScout. Это не HTTP API: PySide6 UI и CLI используют один Dispatcher, Registry и application services. Машиночитаемая форма команд и ошибок — `api/commands.schema.json`; архитектура и Job lifecycle — `architecture.md`; Tool API — `tool-contract.md`.

| Карта | Ответ контракта |
|---|---|
| **К1 Двойной клик** | Для одного пользовательского действия UI создаёт один `request_key` и повторно использует его для всех отправок, включая клик-дубликат через 100 мс. Dispatcher атомарно создаёт одну Job; второй `jobs.create` с тем же ключом и тем же payload возвращает тот же `job_id`, текущее состояние и `replayed=true`. Другой payload с тем же ключом → `IDEMPOTENCY_KEY_REUSED`, без второй Job. `api/commands.schema.json` (`createJob`, `request_key`, `successEnvelope`); ADR-0004. |
| **К2 Ответ потерялся** | Клиент сохраняет `request_key` до отправки команды. Если Job создана, но ответ потерян, клиент повторяет `jobs.create` с тем же ключом и тем же payload; Dispatcher возвращает прежний `job_id` и `replayed=true`. Повтор не запускает Tool/адаптеры заново. Если ключ утерян, клиент не генерирует новый автоматически: сначала восстанавливает сохранённый pending request из локального хранилища; иначе нельзя безопасно отличить повтор от нового намеренного поиска. `api/commands.schema.json` (`createJob`); ADR-0004. |
| **К3 Неизвестная операция** | Неизвестное значение `command` отклоняется Dispatcher до вызова Registry: `UNKNOWN_COMMAND`, `field=command`, `details.allowed_commands` содержит список доступных операций. Job не создаётся и Tools не вызываются. Некорректный JSON возвращает `INVALID_JSON` без `field`; синтаксически корректная команда с известным именем, но неверной структурой — `VALIDATION_ERROR`. `architecture.md`, раздел «Ошибки протокола»; `api/commands.schema.json`, `errorEnvelope`. |
| **К4 Кривые параметры** | Отсутствующее обязательное поле, неверный тип, лишнее поле или недопустимая длина отклоняются до создания Job: `VALIDATION_ERROR`, `field` содержит путь проблемного поля (например, `edition.isbn`), `details.violations[]` — `path`, `rule`, `expected`, `actual`. Семантическая проверка контрольной цифры ISBN выполняется `ValidateIsbnTool`; для корректно сформированной команды с неверной контрольной цифрой создаётся Job, которая завершается `FAILED` с `ISBN_CHECKSUM_INVALID`, `field=isbn`. `api/commands.schema.json`; `tool-contract.md`; `architecture.md`, раздел 6. |
| **К5 Воскрешение** | Терминальную Job нельзя переводить обратно в `CREATED` или повторно исполнять. `jobs.retry` разрешён для терминальной Job и создаёт новую Job с новым `job_id`, `parent_job_id` равным ID исходной Job и новым `request_key`; прежнее состояние, ошибки и результаты остаются неизменными. Повтор `jobs.retry` с тем же ключом возвращает уже созданную дочернюю Job. Попытка прямого перехода из терминального состояния → `409`-эквивалент `JOB_TERMINAL` / `JOB_INVALID_TRANSITION`. `architecture.md`, диаграмма состояний и таблица переходов; `api/commands.schema.json` (`retryJob`); ADR-0004. |
| **К6 Отмена** | `jobs.cancel` разрешена в `CREATED`, `VALIDATING`, `RESOLVING_BOOK`, `FETCHING_OFFERS`; Job становится `CANCELLED`. Уже подтверждённые и сохранённые результаты источников остаются прикреплёнными к Job и могут быть показаны с пометкой «поиск отменён»; незавершённые запросы отменяются best-effort. Поздние ответы игнорируются. В `NORMALIZING` отмена уже не поддерживается: ответ `JOB_INVALID_TRANSITION`; повторная отмена `CANCELLED` идемпотентно возвращает текущий снимок. `architecture.md`, диаграмма и запрещённые переходы; `api/commands.schema.json` (`cancelJob`); ADR-0002. |
| **К7 Огромный вход** | На входном слое установлен предел 16 KiB на одну JSON-команду и глубина вложенности не более 8. Текстовое название — до 300 символов, автор — до 200; ISBN — до 17 символов с разделителями. Превышение общего лимита → `REQUEST_TOO_LARGE`, `field=null`, `details.max_bytes=16384`, `actual_bytes`; превышение лимита конкретного поля → `VALIDATION_ERROR` с `field` этого поля. Отказ происходит до создания Job, записи в SQLite и сетевых вызовов. `architecture.md`, раздел «Ошибки протокола»; `api/commands.schema.json` (ограничения `maxLength`); `tool-contract.md`. |
| **К8 Чужой или несуществующий id** | BookScout — локальное однопользовательское desktop-приложение: Job хранится в SQLite-профиле текущего OS-пользователя, удалённые аккаунты и межпользовательский API отсутствуют. Для неизвестного `job_id` возвращается `JOB_NOT_FOUND` с одинаковым телом независимо от причины; данные других OS-профилей недоступны через приложение и защищены ACL ОС. Dispatcher не возвращает частичные сведения о неизвестной Job. Если появится серверный/multi-user режим, потребуется отдельный механизм владельца и авторизации до выдачи Job. `architecture.md`, разделы 1, 5 и 6; ADR-0001 и ADR-0003. |
| **К9 Перезапуск сервера** | Серверного процесса нет; эквивалентная ситуация — аварийный перезапуск desktop-приложения при нетерминальной Job. При старте recovery находит `CREATED`, `VALIDATING`, `RESOLVING_BOOK`, `FETCHING_OFFERS`, `NORMALIZING` и переводит их в `FAILED` с `error_code=APP_RESTARTED`. Уже транзакционно сохранённые результаты и source statuses сохраняются; незавершённые сетевые вызовы не возобновляются. Пользователь запускает новую Job через `jobs.retry` или новый поиск; прежняя Job остаётся доступна в истории. `architecture.md`, разделы 4–6; ADR-0002, ADR-0003. |
| **К10 Внешний сервис** | Каждый адаптер имеет timeout 8 секунд, общий deadline Job — 15 секунд. Таймаут → `STORE_TIMEOUT`; недоступность/5xx → `STORE_UNAVAILABLE`; невалидный JSON, переименование обязательного поля или нарушение схемы → `STORE_RESPONSE_INVALID`. Ошибка одного магазина изолирована: другие адаптеры продолжают работу. Есть валидные Offers и ошибка источника → `PARTIAL`; все источники ответили корректно, но Offers нет → `NO_RESULTS`; ни один источник не дал пригодного ответа до deadline → `TIMED_OUT`; все ответы протокольно некорректны и пригодных данных нет → `FAILED`. Клиент видит `source_results` с `success/error/timeout` и кодом ошибки; автоматические повторы допускаются только для временных ошибок и в пределах общего deadline. `tool-contract.md`, `SearchStoreOffersTool`; `architecture.md`, разделы 3–6; `api/commands.schema.json`. |
| **Джокер: один ответ магазина содержит и валидные, и испорченные Offers** | Адаптер валидирует каждый элемент отдельно. Валидные элементы сохраняются; испорченные отбрасываются и учитываются как ошибка источника `STORE_RESPONSE_INVALID` с индексом элемента в диагностике. Если после нормализации остался хотя бы один валидный Offer, Job завершается `PARTIAL`, а не `FAILED`; исходный мусор не попадает в UI/кэш. `tool-contract.md`, раздел `SearchStoreOffersTool`; `architecture.md`, раздел 3. |

## Единый формат ошибок

Все ошибки локального протокола имеют одну JSON-оболочку:

```json
{
  "ok": false,
  "request_id": "4f0b4b7e-8c44-4b1a-a40c-7a3a08a8d5f2",
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Поле title превышает допустимую длину",
    "field": "query.title",
    "retryable": false,
    "details": {
      "violations": [
        {"path": "query.title", "rule": "maxLength", "expected": 300, "actual": 450}
      ]
    }
  }
}
```

`request_id` возвращается, если его удалось извлечь из корректного envelope; при ошибке JSON parsing он может отсутствовать. `field` — путь проблемного поля или `null`, если ошибка не относится к одному полю. `details` всегда объект. `retryable` показывает, имеет ли смысл повторить ту же команду без изменения параметров.

| Код | Условие | `field` | Создаётся Job? |
|---|---|---|---|
| `INVALID_JSON` | Вход не разбирается как JSON | `null` | Нет |
| `UNKNOWN_COMMAND` | Неизвестное имя операции | `command` | Нет |
| `VALIDATION_ERROR` | Неверная форма/тип/размер поля | Путь поля | Нет |
| `REQUEST_TOO_LARGE` | Команда больше 16 KiB или глубина больше 8 | `null` | Нет |
| `IDEMPOTENCY_KEY_REUSED` | Ключ повторён с другим payload | `request_key` | Нет новой Job |
| `JOB_NOT_FOUND` | Job не найдена в локальном профиле | `job_id` | Нет |
| `JOB_TERMINAL` / `JOB_INVALID_TRANSITION` | Запрещённая операция над Job | `target_state` или `job_id` | Нет |
| `ISBN_CHECKSUM_INVALID` | ISBN не прошёл семантическую проверку | `isbn` | Да, Job завершается `FAILED` |
| `STORE_TIMEOUT` / `STORE_UNAVAILABLE` / `STORE_RESPONSE_INVALID` | Ошибка отдельного источника | `null` либо путь элемента | Уже созданная Job; статус источника обновляется |
| `STORAGE_ERROR` | Ошибка SQLite | `null` | Создание не подтверждается; при ошибке записи результата возвращается ошибка хранения |

CLI exit codes: `0` — успех; `2` — ошибка ввода/команды; `3` — не найдено; `4` — конфликт состояния или идемпотентности; `5` — timeout; `6` — внешняя зависимость; `7` — хранилище/внутренняя ошибка; `130` — отмена пользователем.

## Что предложил ИИ

### Промпт атакующего

> Ты — атакующий QA-архитектор. Изучи контракт BookScout: `architecture.md`, `api/commands.schema.json`, `tool-contract.md`, ADR-0001–ADR-0004 и таблицу покерных карт K1–K10 с Джокером ниже. Найди ровно три дополнительные ситуации, которые не дублируют карты. Для каждой опиши предусловие, последовательность действий, ожидаемый сбой, недостающее правило и минимальный проверочный тест. Ищи проблемы на границах транзакций SQLite, конкурентных вызовов, кэша, нормализации цены и открытия внешних ссылок. Не предлагай решение, которое противоречит ограничениям desktop MVP.

### Находка 1. Два процесса одновременно создают Job с одним request_key

- **Риск:** UI и CLI одновременно отправляют одну команду; оба потока предварительно не видят ключ и пытаются создать Job.
- **Решение: принято.** Уникальность `request_key` обеспечивается ограничением SQLite, а не предварительной проверкой в памяти. Проигравшая транзакция перечитывает запись и возвращает существующую Job, если payload hash совпадает; иначе возвращает `IDEMPOTENCY_KEY_REUSED`.
- **Тест:** запустить два конкурентных `jobs.create` с одним ключом и одинаковым payload; в БД одна Job, оба ответа содержат один `job_id`.

### Находка 2. Цена корректна по типу, но отрицательна или переполняет допустимый диапазон

- **Риск:** значение проходит поверхностную проверку типа, но даёт бессмысленную цену либо вызывает ошибку преобразования/сортировки.
- **Решение: принято.** `price_minor` и `delivery_minor` должны быть целыми неотрицательными числами в пределах `0..100000000000`; валюта — только `RUB`. Нарушивший правило Offer отбрасывается с `OFFER_PRICE_INVALID` или `OFFER_CURRENCY_UNSUPPORTED`, остальные элементы продолжают обрабатываться.
- **Тест:** адаптер возвращает Offers с `price_minor=-1`, строковой ценой, чрезмерным числом и `currency=USD`; ни один невалидный Offer не появляется в выдаче.

### Находка 3. Проверенная HTTPS-ссылка перенаправляет на другой домен

- **Риск:** исходный URL принадлежит allowlist, но HTTP redirect ведёт на посторонний домен или небезопасную схему.
- **Решение: принято.** При открытии ссылки проверяется не только исходный URL, но и конечный URL после redirect (если redirect проверяется до открытия). Внешний переход разрешён только по HTTPS и на домен из allowlist; если безопасно проверить цепочку до передачи браузеру невозможно, ссылка не открывается и показывается `OFFER_URL_REJECTED`.
- **Тест:** mock-ответ магазина возвращает разрешённый URL с redirect на посторонний домен; системный браузер не вызывается.
