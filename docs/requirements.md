# Требования к BookScout MVP

## 1. Цель и границы

BookScout --- desktop-приложение для Windows и macOS (первая проверка
сборки --- на одной целевой ОС), которое принимает ISBN или текстовое
название книги, помогает выбрать конкретное издание и сравнивает
доступные предложения подключённых российских магазинов.

**Основная ценность:** пользователь видит сопоставимые предложения и
может открыть страницу магазина, не выполняя поиск вручную на каждом
сайте.

### Термины

-   **Книга / издание** --- библиографическая запись с названием,
    автором и, если доступен, ISBN.
-   **Offer (предложение)** --- найденная карточка товара магазина с
    ценой, ссылкой и метаданными.
-   **Источник** --- магазин или легальный поставщик данных о его
    товарах.
-   **Job** --- одна пользовательская задача поиска и сравнения.
-   **Сопоставимое предложение** --- предложение, для которого ISBN
    совпадает с выбранным изданием либо совпадение подтверждено по
    согласованным правилам fallback.

### Предположения и ограничения

-   Валюта MVP --- RUB.
-   Для сравнения по ISBN приоритет имеет точное совпадение ISBN-13.
    ISBN-10 нормализуется в ISBN-13, если преобразование валидно.
-   Для текстового запроса приложение показывает варианты изданий;
    пользователь выбирает нужное, если однозначность не достигнута.
-   Цена и наличие могут измениться после получения результата. В
    интерфейсе обязательно отображается время проверки.
-   Доставка может быть неизвестна или зависеть от региона. Неизвестная
    доставка не трактуется как ноль.
-   В MVP включаются только источники, для которых подтверждён
    допустимый способ получения данных. Конкретный список источников
    фиксируется отдельной конфигурацией релиза.

## 2. Функциональные требования и сценарии

### Сценарий 1. Поиск по ISBN

**Цель:** получить предложения для конкретного издания без
неоднозначности текстового поиска.\
**Участник:** покупатель книги.

**Основной поток:** 1. Пользователь открывает BookScout. 2. Вводит
ISBN-10 или ISBN-13 в поле поиска. 3. Приложение валидирует контрольную
цифру и нормализует ISBN. 4. Приложение получает библиографические
данные книги. 5. Приложение создаёт Job и запрашивает предложения у
включённых источников. 6. Приложение показывает найденные предложения,
время проверки и состояние каждого источника.

**Критерии приёмки:** - **Дано** корректный ISBN-13, **когда**
пользователь запускает поиск, **тогда** приложение создаёт Job и
показывает результаты именно для найденного ISBN. - **Дано** ISBN-10,
который можно преобразовать, **когда** пользователь запускает поиск,
**тогда** приложение нормализует его и выполняет поиск по каноническому
ISBN-13. - **Дано** некорректный ISBN, **когда** пользователь запускает
поиск, **тогда** приложение показывает понятную ошибку валидации и не
обращается к магазинам.

### Сценарий 2. Поиск по названию и выбор издания

**Цель:** найти книгу, когда ISBN неизвестен.\
**Участник:** покупатель книги.

**Основной поток:** 1. Пользователь вводит название; при возможности
добавляет автора. 2. Приложение ищет библиографические совпадения. 3.
Приложение показывает список кандидатов с названием, автором, ISBN,
годом и издательством (если данные доступны). 4. Пользователь выбирает
нужное издание. 5. Приложение запускает Job сравнения цен для выбранного
издания. 6. Приложение показывает предложения.

**Критерии приёмки:** - **Дано** запрос, по которому найдено несколько
изданий, **когда** поиск завершён, **тогда** приложение показывает
варианты и не сравнивает их до выбора пользователя. - **Дано** выбранное
издание с ISBN, **когда** пользователь подтверждает выбор, **тогда** все
источники получают один и тот же идентификатор издания. - **Дано**
найден один кандидат с достаточной уверенностью, **когда** поиск
завершён, **тогда** приложение всё равно показывает его
библиографические данные и позволяет пользователю подтвердить выбор до
сравнения.

### Сценарий 3. Просмотр и сравнение предложений

**Цель:** понять, где доступно наиболее выгодное предложение.\
**Участник:** покупатель книги.

**Основной поток:** 1. После завершения запросов источников приложение
собирает Offer. 2. Приложение нормализует цены в RUB, ссылки, наличие и
время получения. 3. Приложение удаляет дубликаты одного предложения в
пределах источника. 4. Приложение сортирует предложения по цене товара;
если доставка известна --- дополнительно показывает итоговую сумму
«товар + доставка». 5. Пользователь нажимает «Открыть магазин» у
выбранного предложения.

**Критерии приёмки:** - **Дано** два или более сопоставимых предложения
с известной ценой, **когда** результаты отображены, **тогда** они
отсортированы по цене товара по возрастанию. - **Дано** стоимость
доставки неизвестна, **когда** приложение показывает предложение,
**тогда** оно явно пишет «доставка не указана» и не считает её равной
нулю. - **Дано** пользователь нажимает ссылку предложения, **когда**
ссылка валидна, **тогда** приложение открывает карточку товара во
внешнем браузере. - **Дано** цена получена ранее, **когда** приложение
показывает её из кэша, **тогда** рядом отображается время последней
проверки и отметка «из кэша».

### Сценарий 4. Частичная недоступность магазинов

**Цель:** получить полезный результат, даже если один источник не
отвечает.\
**Участник:** покупатель книги; система источников.

**Основной поток:** 1. Приложение запускает запросы к подключённым
источникам независимо. 2. Каждый адаптер возвращает предложения либо
типизированную ошибку/тайм-аут. 3. Приложение ждёт завершения запросов
до общего deadline. 4. Приложение показывает результаты успешных
источников и отдельный статус недоступных источников. 5. Пользователь
может повторить запрос к недоступным источникам.

**Критерии приёмки:** - **Дано** один источник завершился тайм-аутом, а
другой вернул предложения, **когда** Job достиг deadline, **тогда**
приложение показывает предложения успешного источника и отмечает первый
как «не удалось проверить». - **Дано** все источники недоступны,
**когда** Job завершён, **тогда** приложение показывает сообщение об
отсутствии проверенных предложений, а не сообщение «книга нигде не
продаётся». - **Дано** пользователь нажимает «Повторить», **когда** Job
находится в состоянии завершения с ошибками, **тогда** создаётся новая
Job или новый запуск с отдельным идентификатором.

### Сценарий 5. Отмена и повторный поиск

**Цель:** управлять длительным поиском и не перепутать результаты
нескольких запросов.\
**Участник:** покупатель книги.

**Основной поток:** 1. Пользователь запускает поиск. 2. Приложение
отображает прогресс и возможность отмены. 3. Пользователь отменяет Job
либо запускает новый поиск. 4. Приложение отменяет ещё не завершённые
запросы предыдущей Job, где это поддерживается. 5. Результаты предыдущей
Job не должны перезаписать результаты текущего поиска.

**Критерии приёмки:** - **Дано** Job выполняется, **когда** пользователь
нажимает «Отмена», **тогда** Job переходит в `CANCELLED`, а UI
прекращает показывать его как активный. - **Дано** запущена Job A и
затем Job B, **когда** ответы A приходят после старта B, **тогда** UI не
подменяет результат B данными A. - **Дано** Job отменена, **когда**
поздно приходит ответ адаптера, **тогда** он не меняет финальное
состояние Job и не добавляется к результатам активного поиска.

## 3. Нефункциональные требования

-   UI не должен зависать во время сетевых запросов.
-   Тайм-аут отдельного источника по умолчанию --- 8 секунд; общий
    deadline Job --- 15 секунд. Значения конфигурируются.
-   Ошибка одного адаптера не должна останавливать остальные адаптеры.
-   Для каждого Offer сохраняются `fetched_at`, источник и исходная
    ссылка.
-   Кэш результатов имеет TTL по умолчанию 30 минут; пользователь может
    принудительно обновить поиск.
-   Секреты API и токены не хранятся в исходном коде и логах.
-   Логи не должны содержать лишние персональные данные; запросы
    пользователя хранятся локально только в объёме, необходимом для
    истории и диагностики.
-   Источники подключаются через общий интерфейс `StoreAdapter`;
    бизнес-логика сравнения не содержит условий, зависящих от
    конкретного магазина.
-   До включения источника в релиз проверяются условия использования,
    ограничения частоты запросов и допустимость выбранного способа
    доступа.

## 4. Жизненный цикл Job

Состояния: - `CREATED` --- Job создана, параметры запроса
зафиксированы. - `VALIDATING` --- проверяется и нормализуется ISBN либо
текстовый запрос. - `RESOLVING_BOOK` --- определяется библиографическая
запись/издание. - `FETCHING_OFFERS` --- выполняются запросы к адаптерам
магазинов. - `NORMALIZING` --- результаты приводятся к общей модели,
проверяются и сортируются. - `SUCCEEDED` --- получен хотя бы один
валидный сопоставимый Offer; задача успешно завершена. - `PARTIAL` ---
часть источников завершилась ошибкой, но полезные предложения
получены. - `NO_RESULTS` --- источники проверены, но сопоставимых
предложений не найдено. - `FAILED` --- задача не смогла завершиться
из-за фатальной ошибки до получения пригодного результата. - `CANCELLED`
--- пользователь отменил Job. - `TIMED_OUT` --- общий deadline истёк,
полезный результат не получен.

Разрешённые переходы: - `CREATED → VALIDATING` -
`VALIDATING → RESOLVING_BOOK` --- для текстового запроса или ISBN после
успешной валидации. - `VALIDATING → FAILED` --- невалидный ввод или
ошибка нормализации. - `RESOLVING_BOOK → FETCHING_OFFERS` --- издание
определено/подтверждено. - `RESOLVING_BOOK → FAILED` --- не удалось
определить книгу из-за фатальной ошибки. -
`FETCHING_OFFERS → NORMALIZING` --- получены ответы либо достигнут
deadline сбора. - `FETCHING_OFFERS → TIMED_OUT` --- deadline истёк и нет
результатов для нормализации. - `NORMALIZING → SUCCEEDED` --- все
необходимые запросы успешны и найдено хотя бы одно предложение. -
`NORMALIZING → PARTIAL` --- найдено хотя бы одно предложение, но один
или несколько источников завершились ошибкой. -
`NORMALIZING → NO_RESULTS` --- проверенные источники не вернули
сопоставимых предложений. - `NORMALIZING → FAILED` --- ошибка обработки
не позволяет доверять результатам. -
`CREATED | VALIDATING | RESOLVING_BOOK | FETCHING_OFFERS → CANCELLED`
--- пользователь отменил Job. -
`SUCCEEDED | PARTIAL | NO_RESULTS | FAILED | CANCELLED | TIMED_OUT` ---
терминальные состояния; переходов из них нет. Повтор создаёт новую Job.

## 5. Что предложил ИИ

**Промпт, использованный для дополнительного анализа:**

> Ты --- QA-инженер, который пытается сломать desktop-приложение
> BookScout. Основной сценарий: пользователь вводит ISBN или название
> книги, выбирает конкретное издание, приложение параллельно получает
> предложения российских магазинов, сравнивает цены и открывает ссылку
> магазина. Предложи ещё 3 реалистичных способа сломать этот сценарий,
> которые не дублируют уже описанные ошибки (невалидный ISBN,
> неоднозначное издание, тайм-аут источника, отмена Job и поздний ответ
> старой Job). Для каждого опиши предусловие, последовательность
> действий, ожидаемое некорректное поведение и тест, который должен его
> обнаружить. Учитывай ISBN, разные издания, цены, кэш и внешние ссылки.

### Предложение 1. Магазин вернул цену в копейках, а адаптер трактовал её как рубли

-   **Риск:** цена `79900` отображается как 79 900 ₽ вместо 799 ₽ либо
    наоборот.
-   **Решение:** **принято**. В контракте адаптера цена хранится в
    минимальных денежных единицах (`price_minor`) или в Decimal с явно
    заданной валютой; преобразование в UI выполняется в одном месте.
-   **Дополнительный тест:** адаптер возвращает цену 79 900 копеек; UI
    должен показать 799,00 ₽.

### Предложение 2. Кэш вернул предложение для старого ISBN или другого выбранного издания

-   **Риск:** ключ кэша построен только по названию, поэтому разные
    издания получают чужие цены.
-   **Решение:** **принято**. Ключ кэша включает канонический ISBN,
    идентификатор источника и версию схемы нормализации. Для предложений
    без ISBN кэширование в MVP отключается либо применяется отдельная
    короткоживущая стратегия с подтверждённым fingerprint.
-   **Дополнительный тест:** два издания с одинаковым названием и
    разными ISBN не должны разделять записи кэша.

### Предложение 3. Ссылка магазина ведёт на другой товар или содержит небезопасную схему

-   **Риск:** источник вернул устаревшую/подменённую ссылку, редирект
    ведёт не на карточку товара или ссылка использует
    `javascript:`/`file:`.
-   **Решение:** **принято**. Разрешать только `https`; валидировать
    домен по allowlist источника; сохранять исходный URL и не открывать
    произвольные схемы. Редиректы проверяются по возможности.
-   **Дополнительный тест:** ссылка с `javascript:` и ссылка на
    посторонний домен не должны открываться.

## 6. Открытые вопросы перед релизом

1.  Какие магазины предоставляют подходящий официальный API, партнёрский
    фид или иной разрешённый канал получения цены?
2.  Какие два источника дают достаточное покрытие книжного ассортимента
    для первой версии?
3.  Нужна ли поддержка Linux в первой поставке или достаточно
    Windows/macOS?
4.  Какой поставщик библиографических данных обеспечивает приемлемое
    покрытие российских изданий и допускает нужный режим использования?
5.  Можно ли получать доставку без адреса пользователя? Если нет --- в
    MVP показываем её как неизвестную.
